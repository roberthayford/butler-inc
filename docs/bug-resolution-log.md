# Bug Resolution Log

Tracks significant bugs, their root causes, and lessons learned to inform future development.

## Format

Each entry follows this structure:

### [Date] — Short description
- **Symptom:** What was observed
- **Root cause:** Why it happened
- **Fix:** What was changed (commit ref if useful)
- **Lesson:** What to watch for in future work

### 2026-06-07 — Butler page copy edits to static files don't reach the live site
- **Symptom:** Founder feedback (written against staging.butlersinc.com) referenced butler hero/trust/common-request copy that the `staging` branch code had already removed/cleaned — e.g. "fully-booked Michelin", "sold-out West End", "high-net-worth clients", "accompany child to medical appointment", and `Insured for items up to £5,000` (static says £50,000). The static `butler-content.test.ts` was green, yet the live site showed the old strings. The live commonRequests also still contained **em dashes**, violating the project's #1 copy rule, despite the static em-dash cleanup (commit `0d96fb3`).
- **Root cause:** `src/app/butlers/[id]/page.tsx` reads a `site_content` row from Supabase and `mergeContent()` (`src/lib/content.ts`) **fully overrides** `hero.headline`, `hero.subheading`, `trustIndicators`, and `commonRequests` when a row exists. All 6 butlers have rows, seeded by `scripts/seed-content.ts` BEFORE the content-safety pass (`e54c0c0`) and em-dash cleanup (`0d96fb3`). So the static files are only the fallback; the live site is served stale DB content. `butler-content.test.ts` only asserts on the static fallback, giving false confidence.
- **Fix:** (in progress) Route copy edits to the correct layer: task-label edits to `butler-tasks.ts` (not overridden, reflects live); hero/trust/commonRequests edits update the `site_content` DB rows (migration or re-seed) AND keep `butler-page-configs.ts` in sync. Add a test that guards the actual served content (DB seed shape), not just the static fallback. Strip em dashes from the DB rows.
- **Lesson:** Before editing customer-facing copy, confirm WHICH layer serves it. The CMS override (`site_content`) silently wins over static data for `hero`/`trustIndicators`/`commonRequests`. A green static-content test does not prove the live site is correct: the test must cover the data actually rendered. When cleaning content (em dashes, risky examples), clean the DB too, not just the source files.

### 2026-05-29 — Member prepaid bookings still sent users to payment
- **Symptom:** Active members booking a self-service butler from their account had prepaid hours deducted correctly, but the flow still sent them to checkout and asked for payment.
- **Root cause:** `/api/create-checkout-session` checked that active members had enough personal butler hours, but then always created a payment checkout session. The hour deduction only happened later in the payment-complete webhook, so prepaid bookings were coupled to payment.
- **Fix:** Active members with enough remaining hours now skip checkout: the API inserts the booking, deducts prepaid hours with an optimistic lock, confirms the booking, and returns the booking-confirmation URL. Active members without enough prepaid hours still proceed to checkout at a member paid rate.
- **Lesson:** Membership pricing and membership prepaid allowance are related but distinct. Active member bookings covered by remaining allowance must not enter payment checkout; overage/used-up allowance bookings may enter checkout.

### 2026-03-31 — Invisible content on client-side navigation
- **Symptom:** Sections disappeared when navigating between butler pages via client-side routing
- **Root cause:** `whileInView` Framer Motion animations don't re-trigger on client-side navigation because the elements are already in the viewport when the component mounts
- **Fix:** Replaced `whileInView` with `animate` for entrance animations on butler pages (commit `337a9fc`)
- **Lesson:** Avoid `whileInView` for content that must be visible on client-side nav. Use `animate` with `viewport={{ once: true }}` or check mount state.

### 2026-03-31 — Non-admin users could access /admin page
- **Symptom:** Any authenticated user could view the admin panel
- **Root cause:** No server-side or client-side admin check on the `/admin` route
- **Fix:** Added admin email check to restrict access (commits `c18d809`, `c99f1ce`)

### 2026-05-23 — Signed-in booking forms asked for account identity again
- **Symptom:** Signed-in users opening booking forms were still asked for their name and email.
- **Root cause:** Booking form validation and API payloads treated name/email as client-entered fields for every user, even though authenticated users already have those details in Supabase auth metadata.
- **Fix:** Hide name/email fields for authenticated booking forms and have booking APIs override submitted contact identity from `auth.getUser()`.
- **Lesson:** For authenticated flows, derive account identity server-side and only ask for intake details that are booking-specific.

### 2026-05-24 — Confirm-email button in signup emails sent users to `http://localhost:3000/?code=…`
- **Symptom:** The "Confirm your email" button in Supabase signup emails landed users on `http://localhost:3000/?code=…` instead of the deployed site, and the `?code=…` was silently dropped without signing the user in.
- **Root cause:** Three layered defects — (a) Supabase project's **Site URL** was still the default `http://localhost:3000`; (b) neither `signUp()` call site (`src/context/AuthContext.tsx`, `src/app/api/members/signup/route.ts`) passed `options.emailRedirectTo`, so the app could not pick the right origin per environment (prod/staging/preview/local); (c) no `/auth/callback` route existed to call `exchangeCodeForSession(code)` and persist the session.
- **Fix:** Added `src/lib/site-url.ts` (`getSiteUrl(request?)`) that prefers the request origin then `NEXT_PUBLIC_SITE_URL`; both signup paths now pass `emailRedirectTo: ${origin}/auth/callback`; new `src/app/auth/callback/route.ts` exchanges the code and redirects to `?next=` (default `/members/dashboard`) with an open-redirect guard. Supabase dashboard updated (Site URL → `https://staging.butlersinc.com`; Redirect URL allowlist gained `…/auth/callback` for prod, staging, and localhost) and `NEXT_PUBLIC_SITE_URL` set per Vercel environment.
- **Lesson:** For any Supabase magic-link / confirm-email / reset-password flow, always pass `emailRedirectTo` explicitly *and* keep a matching callback route. The dashboard's **Site URL** is a single global fallback, it cannot serve multiple environments at once.

### 2026-05-24 — "The string did not match the expected pattern" toast on booking submit
- **Symptom:** Customer tried to make a payment on a butler page and saw a Sonner toast with the cryptic message "The string did not match the expected pattern". The error was opaque to the user, gave no actionable info, and persisted across reloads.
- **Root cause (probable):** Vercel had `SUPABASE_SERVICE_ROLE_KEY` flagged as "Needs Attention" (empty or invalid value). `/api/create-checkout-session` calls `createServiceClient()` at line 103 outside the route's try/catch. With a missing key, supabase-js throws "supabaseKey is required" synchronously. Next.js then returns a default 500 page with an HTML body, not JSON. The client did `await res.json()`, which calls `JSON.parse(htmlString)`. **Safari/WebKit's JSON.parse error message is exactly "The string did not match the expected pattern"** (Chrome and Firefox produce different wording). The outer `catch (err)` then did `toast.error(err.message)`, surfacing Safari's internal message verbatim to the customer.
- **Fix (root cause):** Re-set `SUPABASE_SERVICE_ROLE_KEY` in Vercel (Project → Settings → Environment Variables) with the live value from Supabase API settings. The "Needs Attention" badge clears once the value is valid.
- **Fix (defense in depth):** Wrapped the top-level `POST` handler in `/api/create-checkout-session/route.ts` and `/api/bookings/route.ts` in a try/catch that always returns JSON 500 with the underlying error message, and added a `readErrorMessage()` helper in `src/components/booking/BookingFlow.tsx` that falls back to `Booking failed (HTTP <status>)` when the response body cannot be parsed as JSON. Future misconfigurations now surface useful messages client-side instead of Safari's `JSON.parse` error.
- **Lesson:** Any Next.js route handler can throw before its first `NextResponse.json(...)` — `createClient()`, `createServiceClient()`, `await request.json()`, factory functions, all are unhandled-throw candidates. Wrap the entire handler body in a try/catch so the response is **always** a JSON envelope. On the client, never call `res.json()` without falling back to `res.text()` or a status message when the response body isn't JSON. Also: Safari's `JSON.parse` error message is its own signature, useful for triaging "response was HTML, not JSON" symptoms.

### 2026-05-24 — "Payment verification failed" on every mock checkout in Vercel
- **Symptom:** Customer reached the simulated payment page (`/payment/simulate?session_id=...`), clicked "Pay £125.00", and saw "Payment verification failed". Reproducible every time.
- **Root cause:** `MockPaymentGateway` tracked issued session IDs in a `private sessions = new Set<string>()` instance field. `getPaymentGateway()` returns `new MockPaymentGateway()` on every call, and `/api/create-checkout-session` + `/api/webhooks/payment-complete` are separate routes hitting separate serverless invocations. The Set in the verify-time gateway was never the same Set the create-time gateway added to, so `sessions.has(sessionId)` was always false. The check returned `verified: false` and the webhook responded with "Payment verification failed". This bug pre-dated Phase A; it was only working locally where Node module reuse + same-request gateway instance happened to coincide.
- **Fix:** Replace Set-membership verification with prefix-pattern verification (`sessionId.startsWith("mock_session_")`). Replay protection moves to the DB layer where it already lives: `booking_repository.findByCheckoutSession` returns null for unknown session IDs (yields a 404 at the webhook), and the webhook short-circuits with `already_processed` when `booking.payment_status === "paid"`. Two now-obsolete tests for "fabricated mock session IDs" and "replay rejection" rewritten to lock in the new design.
- **Lesson:** Cross-request state in serverless functions cannot live in instance fields. If a mock gateway needs to track "I issued this token", it must either use a module-level static singleton (works within one Node process but resets on cold-start) or delegate to a persistent store (DB, KV, etc.). For mocks specifically, prefer pattern-based verification with replay protection at the database layer, mirroring how real Stripe verifies signatures without server-held state.

### 2026-05-24 — "Booking not found" on payment-complete in local dev with DEV_BYPASS_DB=true
- **Symptom:** Locally with `DEV_BYPASS_DB=true`, booking submission succeeded (`POST /api/create-checkout-session 200`) but the immediately-following `POST /api/webhooks/payment-complete` returned 404 "Booking not found". The in-memory dev store appeared empty even though a booking had just been inserted milliseconds before.
- **Root cause:** `booking-repository.ts` held the dev singleton in a module-level `let devStoreInstance: DevBookingStore | null = null`. In **Next.js App Router dev mode**, each route handler can re-evaluate its dependency module graph independently, so `/api/create-checkout-session` and `/api/webhooks/payment-complete` each ended up with their own copy of `booking-repository.ts`, each with their own `devStoreInstance = null`, each instantiating a fresh empty `DevBookingStore`. The booking inserted in one route's store was invisible to the lookup in the other route's store.
- **Fix:** Move the singleton onto `globalThis`. `globalThis.__butlersDevStore` survives Next.js dev module re-evaluation across route handlers, so both routes share the same in-memory `Map`. Standard Next.js dev-singleton pattern, the same one Prisma docs recommend for `PrismaClient`.
- **Lesson:** In Next.js App Router dev mode, module-level singletons (`let x = null`) don't reliably persist across route handler boundaries. For anything that must be a true process-wide singleton, attach it to `globalThis`. This only matters in dev; production builds bundle each route handler with its own copy of the module graph anyway, so for production correctness the underlying store must be a real external service (DB, Redis, etc.) regardless.

### 2026-05-24 — Staging deploy failed (`useSearchParams` not in Suspense) + mock gateway threw on staging runtime
- **Symptom (build):** Vercel deploy of commit `ee6e84c` to staging failed with `useSearchParams() should be wrapped in a suspense boundary at page "/members/signup"` during the static prerender pass; build exited 1.
- **Symptom (runtime, previous deploy):** Vercel function logs showed `Error: Mock payment gateway cannot be used in production. Set PAYMENT_GATEWAY=stripe and configure Stripe credentials.` on every booking submit, which (without route-level JSON envelope on every endpoint) yielded HTML 500 → Safari "The string did not match the expected pattern" toast.
- **Root cause (build):** Task 16's SignupPage refactor added `useSearchParams()` to honour `?next=` after signup. Next.js App Router treats pages that call `useSearchParams` as needing a Suspense boundary for static prerendering — without one, the build bails out at prerender time.
- **Root cause (runtime):** `src/lib/payment/gateway.ts` had `if (provider === "mock" && process.env.NODE_ENV === "production") throw`. **Vercel sets `NODE_ENV=production` on every deploy** (Preview, Staging, Production), so the guard fired on the staging deploy too. With no `PAYMENT_GATEWAY` env var explicitly set, the provider defaulted to `"mock"` and the guard threw on every payment call.
- **Fix (build):** Wrap `<SignupPage />` in a `<Suspense>` boundary in `src/app/members/signup/page.tsx`. Same pattern already used in `/payment/simulate/page.tsx`.
- **Fix (runtime):** Replace `NODE_ENV === "production"` with `process.env.VERCEL_ENV === "production"` in the mock-in-prod guard. `VERCEL_ENV` is `"production" | "preview" | "development"`, distinguishing real production from staging/preview. Local dev (no `VERCEL_ENV`) and staging (`preview`) now allow mock; only real Vercel production blocks it. Four-test coverage in `gateway-safety.test.ts` (prod blocks, preview allows, local allows, NODE_ENV no longer the gate).
- **Lesson:** On Vercel, `NODE_ENV` is always `"production"` on every deploy (it controls bundling, not environment semantics). Use `VERCEL_ENV` to distinguish staging from production. Any code path using `NODE_ENV === "production"` to gate behaviour on Vercel is almost certainly wrong. Separately: every client component using `useSearchParams` MUST be wrapped in `<Suspense>` somewhere up its tree, otherwise static prerendering fails the build.

### 2026-05-25 — "Cannot update a component (`Router`) while rendering" on /members/settings
- **Symptom:** Console error on `/members/settings`: `Cannot update a component (Router) while rendering a different component (SettingsPage). To locate the bad setState() call inside SettingsPage, follow the stack trace at SettingsPage (src/app/members/settings/page.tsx:105:16)`. The offending line was `router.push("/members/login")` called synchronously inside the `if (!user)` early-return block.
- **Root cause:** Latent Rules-of-React violation that pre-dated this branch (commit `685f37f`). React 18+ and Next 16 forbid components from triggering state updates in other components during their own render phase. The settings page handled the unauthenticated state with `if (!user) { router.push("/members/login"); return null; }` — the `router.push` call modifies Router state mid-render and trips the warning. The bug was silent until the membership-lifecycle work on this branch added `useMembership()` + `useQueryClient()` + a portal-snapshot effect, which cause more frequent re-renders that hit the `!user` branch visibly in dev under Turbopack.
- **Fix:** Move the redirect into a `useEffect` declared BEFORE the early returns (same React #310 hook-order constraint already documented in the file). Replace the inline `router.push(...)` with a plain `return null;` placeholder while the effect-dispatched navigation kicks in. The effect fires post-commit, so no render-phase state update occurs. Added two regression tests covering the redirect behaviour and the loading-state guard; jsdom + a `vi.fn()` router cannot reliably reproduce the React warning itself (real Router state updates are needed), so the tests regress on behaviour rather than precise timing.
- **Lesson:** `router.push()` (and any other call that updates external state — `setState` on a parent, `dispatch` to a store, etc.) must NEVER run during render. Always wrap auth-redirect logic in `useEffect`. Pre-existing latent bugs of this shape can hide for months and only surface when an unrelated change increases the component's render frequency or strict-mode coverage. When adding new hooks/effects to an existing client component, audit the early-return block for render-phase side effects.
